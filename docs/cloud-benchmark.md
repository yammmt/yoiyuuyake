# 地形データのクラウド配置の検証記録

Issue #36 の構成選定用の記録。測定日は 2026-09-19。
再現手順は[検証コンテナの README](../terrain/benchmark/README.md)にまとめる。

## 採用判断

関東近辺の限定範囲では、Cloud Run＋Cloud Storage＋FUSE ファイルキャッシュを採用する。
固定 7 ケースがすべて成功し、起動待ち込みで約 6.64 秒、再アクセス時のサーバー内部評価は約 0.97 秒だった。
個人の練習用プロジェクトとして、この性能と後述の費用見積もりを許容する。
同条件の追加測定と Compute Engine＋永続ディスクとの実測比較は行わない。
現在の結果で運用を始められると判断したためであり、別基盤より優れることを証明したものではない。

## 結果

| 条件 | HTTP 全体（秒） | サーバー内部の7地点評価（秒） |
| --- | ---: | ---: |
| ローカル HTTP・初回 / 再アクセス | 未計測 | 0.282 / 0.279 |
| Cloud Run・明示的なファイルキャッシュなし・初回 | 152.991 | 152.938 |
| 同条件・再アクセス | 0.863 | 0.820 |
| ファイルキャッシュあり・起動済みインスタンスの初回 | 5.355 | 5.309 |
| 同条件・再アクセス | 未共有（Cloud Run の request latency は 0.972） | 0.970 |
| ファイルキャッシュあり・起動待ち込みの初回 | 6.639 | 5.417 |

初期構成では timeout 120 秒に達して HTTP 504 となった。
測定用に 300 秒へ延長すると全ケース成功したが、初回に約 153 秒かかったため、ファイルキャッシュを有効化した。
その後の表中の呼び出しはすべて HTTP 200、全ケース成功だった。
小さな seek/read を繰り返す処理で、使用するタイル全体をキャッシュする設定が有効だった。

起動待ち込みの計測は、要求・起動・待受が同じ instanceId であることをログで照合した。
以下の時刻は 2026-09-19 の日本時間である。

| イベント | 時刻 |
| --- | --- |
| リクエスト到着 | 22:53:31.049539 |
| インスタンス起動開始 | 22:53:31.076442 |
| サーバー待受開始 | 22:53:32.178116 |

到着から待受まで約 1.13 秒、Cloud Run の request latency は 6.531 秒だった。
前回と異なる `process_id`、`request_sequence=1` も確認した。

| 地点 | 期待値と一致した結果 |
| --- | --- |
| 東京駅 | 広い / 0.951° |
| 秩父 | 一部遮られる / 3.861° |
| 奥多摩 | 遮られやすい / 23.899° |
| 鎌倉 | レイ上の標高欠損 |
| 東京湾 | 観測地点の標高欠損 |
| 西端付近 | レイ上の DEM 範囲外 |
| 範囲外の西側 | 観測地点の DEM 範囲外 |

欠損・範囲外は期待する例外の検出を成功と数え、標高の補完や部分的な評価は行っていない。
キャッシュ有効化後の Python 最大 RSS は約 27.6〜27.9 MiB。
Monitoring のコンテナメモリ使用率は 14:10 JST に p99=23.99%（512 MiB 換算で約 122.8 MiB）だった。

参考として、全国版のローカル検証は 10 ケース成功、経過時間 4.20 / 4.40 / 4.45 秒、最大 RSS 約 25.4 MiB だった。
基準コミットは `75cf7c10f1d1de59b058df9cbe671d2d8c9b8459`。
関東版とはデータ・ケース数・ストアの共有条件が異なるため、直接の速度比較には使わない。

## 読み取り量と費用

DEM バケットの Monitoring CSV を、ALIGN_RATE・60 秒整列・REDUCE_SUM の条件で集計した。
各行のレートに 60 秒を掛け、欠測は補間していない。

| 指標 | 収録範囲（JST） | 集計値 |
| --- | --- | ---: |
| 送信量（`network/sent_bytes_count`） | 14:04〜14:55 の15行 | 104,948,015 bytes（約 100.09 MiB） |
| ListObjects | 13:47〜14:18 の26行 | 58 回 |
| ReadObject | 同上 | 7,619 回 |
| GetObjectMetadata / GetBucketStorageLayout | 同上 | 29 / 6 回 |

ReadObject はキャッシュ設定前の 13:47〜13:50 と 13:57〜14:01 に各 3,749 回、設定後の 14:05〜14:09 に 121 回だった。
これらは収録区間の集計であり、単一リクエストの読み取り量や期間全体の完全な総量ではない。

2026-09-19 に確認した[Cloud Storage 料金](https://cloud.google.com/storage/pricing)による概算は次のとおり。
東京・Standard・単一リージョン・flat namespace を前提とし、税・クレジットを含めない。

| 費目 | 計算 | USD 概算 |
| --- | --- | ---: |
| DEM 保存 / 月 | 0.518712514 GiB × $0.023 | 0.011930 |
| 初回書き込み | 331 / 1,000 × $0.005 | 0.001655 |
| 収録区間の読み取り等 | Class A 58 回 × $0.005/1,000 ＋ Class B 7,654 回 × $0.0004/1,000 | 0.003352 |
| 同じ東京リージョンへの通常のデータ転送 | 無料 | 0 |

操作料金は全件が課金対象の場合の概算で、実請求額ではない。
保存だけなら仮に 1 USD=150 円として約 1.8 円/月となる。
Cloud Run の実行、イメージ・ソース・ログの保存、Maps 等は別費目であり、上表はシステム全体の月額ではない。
[Cloud Build](https://cloud.google.com/build/pricing)の e2-standard-2 は $0.006/分、請求先アカウント全体で月 2,500 分の無料枠がある（同日確認）。

## 制約と引き継ぎ

測定は東京周辺の限定 DEM と固定ケースによる少数回の結果である。
全国対応の MVP 仕様を変更せず、全国配置・任意地点・同時アクセスや、気象取得を含む本番 API の性能は後続のデプロイ・受入確認で扱う。
メモリの p99 は厳密な最大値ではなく、画像ではリビジョンの絞り込みも確認できない。
現在の timeout 300 秒は測定用であり、本番の応答目標ではない。

以下のリソースは削除せず、後続作業への引き継ぎ用として当面保持する。
min 0 でも保存費用は継続し、max 1 は厳密な課金上限にはならない。

| リソース | 用途 |
| --- | --- |
| Cloud Run `dem-benchmark` | 認証付きの固定ケース検証。公開 API には使わない |
| バケット `mapsproduction-507807-dem-benchmark` | 関東近辺 DEM |
| Artifact Registry `dem-benchmark` | 検証イメージ |
| バケット `mapsproduction-507807-build-source` | ビルド用ソース |
| 実行用・ビルド用サービスアカウントと権限 | DEM 読み取りと再ビルド |

本番 API への移行後、不要な検証サービス・イメージ・ソースを整理する。
Firebase Hosting の接続方式と #33 の将来の保存先・追加権限は未確定で、Issue #36 の残る文書化事項である。
