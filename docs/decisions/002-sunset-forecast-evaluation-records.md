# ADR 002: 日没時点の予報と主観評価の記録

## 状態

採用（2026-11-04）。2026-11-05にFirestoreの採用とデータ構造の骨格を追記。詳細なスキーマと実装方式は未決定。

## 背景

初回デプロイは完了している（利用者からの報告）。現在の夕焼けスコアは実際に観察した結果との対応を検証できていない。
評価式の改善に向け、予報の入力気象データと利用者本人の主観評価を対応付けて蓄積する。
本決定はMVPの非対象としていた記録・現地観察を、初回デプロイ後に追加する #33 の設計方針を #53 で記録するものである。

主観評価の入力は毎日あるとは限らず、観察後になることもある。
入力時に過去の気象データを取得しても、日没時点で取得できた予報と同じ情報であるとは扱えない。
予報の取得を主観評価の入力から独立させ、取得タイミングをそろえる必要がある。

利用者にはRDBMSの利用経験があるが、今回はNoSQLを学ぶことも目的とする。

## 決定

- 事前に登録した地点について、毎日その地点の当日の日没時刻に最新の予報を自動取得・保存する。
- 日没前後のスコア計算に使った気象データを保持し、後日の取得データで置き換えない。
- 利用者本人が観察した日の記録に主観評価を手動で追記する。評価の入力日時と実際の観察日時・時間帯を区別する。
- 未観察の日も予報の記録は残し、主観評価は未入力とする。未観察を低評価や0点として扱わない。
- 評価式と主観評価との対応の検証には主観評価がある記録を用いる。
- 記録は永続保存し、分析用に取り出せるようにする。保存・編集の操作は利用者本人に限定する。

### 保存先とデータ構造

保存先をFirestoreとし、登録地点と日次記録を別のコレクションに保存する。

| 保存先 | 役割 |
| --- | --- |
| `locations/{locationId}` | 今後の自動取得に使う地点の設定 |
| `records/{locationId_対象日}` | 1地点・1日分の取得条件、予報、主観評価をまとめた記録 |

日次記録には地点情報も保存し、登録地点の設定を参照しなくても取得条件を確認・分析できるようにする。
`locationId` は登録地点との関連を表し、記録内の地点情報は予報取得時点の情報を表す。
登録地点の設定を変更しても、過去の記録内の地点情報は変更しない。

### 登録地点

| フィールド | 内容 |
| --- | --- |
| `name` | 地点名 |
| `latitude` | 緯度 |
| `longitude` | 経度 |
| `enabled` | 自動取得の対象か |

### 日次記録

以下は構造案であり、型、必須項目、値の検証方法は実装前に決める。

| フィールド | 内容 |
| --- | --- |
| `schemaVersion` | 記録形式のバージョン |
| `locationId` | 登録地点のID |
| `location` | 予報取得時点の地点名・緯度・経度 |
| `targetDate` | 日本時間での対象日 |
| `sunsetAt` | 対象の日没日時 |
| `forecast.fetchedAt` | 実際の予報取得日時 |
| `forecast.source` | 気象データの提供元 |
| `forecast.model` | 使用した気象モデルの識別情報 |
| `forecast.weather` | 計算に使った気象データ一式と、対象時刻・単位 |
| `forecast.scoreVersion` | 評価式のバージョン |
| `forecast.gradient` | Gradientスコア |
| `forecast.dramatic` | Dramaticスコア |
| `observation` | 未入力なら `null`。入力後は以下の観察情報を保存 |
| `observation.observedFrom` | 観察開始日時 |
| `observation.observedTo` | 観察終了日時 |
| `observation.ratings` | 主観評価。項目・尺度は未決定 |
| `observation.memo` | 任意のメモ |
| `observation.enteredAt` | 評価の初回入力日時 |
| `observation.updatedAt` | 評価の最終更新日時 |

日次記録のIDは地点IDと対象日から決め、同じ地点・対象日の記録が重複しないようにする。
定期処理の再実行や主観評価の追記で、保存済みの予報を上書きしない。
IDの具体的な形式と、上書きを防ぐ実装方式は未決定とする。

## 理由

まずは日没時点で取得できる気象予報と実際の夕焼けの見え方を対応付け、評価式を検証する。
数時間前に外出を判断するための予報の有用性は、別の検証課題とする。
自動取得により、主観評価の入力頻度や入力時刻に左右されず、同じ基準で予報を確保できる。
入力気象データを残すことで、新旧の評価式を同じデータに適用して比較できる。

今回の操作は、1地点・1日分の記録の保存・取得と、その記録への主観評価の追記が中心となる。
予報と観察情報を一つの文書にまとめる構造で扱える。
既存の構成でGoogle CloudとFirebaseを利用していることも、Firestoreを選ぶ理由となる。

地点情報の重複は、取得時点の条件を保持するために採用する。
登録地点の設定を参照するだけでは、後日の座標変更によって過去の記録の解釈が変わってしまう。
この履歴保存の必要性は、NoSQLかRDBMSかには依存しない。

## 比較した保存方法

- RDBMSも今回の記録を扱える。SQLによる集計やDB側の制約を重視する場合は有力だが、今回はNoSQLの学習を含めてFirestoreを選ぶ。
- Cloud StorageへのJSON保存も候補としたが、記録の一覧や主観評価の追記を行う用途にはFirestoreを選ぶ。

## 結果と制約

- 日没時点で取得する予報も、実測の気象データとは限らない。主観評価との差には、気象予報の誤差と評価式の問題の両方が含まれる。
- 取得時刻をそろえても、気象モデルの更新時刻や予報の新しさまでそろうとは限らない。
- 日没の3時間前と日没時点で予報がどの程度変化するかは未検証である。
- 未観察の記録だけではスコアの当たり具合を直接検証できない。また、観察した日に偏りがあれば、検証結果にも偏りが生じうる。
- 定期取得・保存と、本人だけが評価を追記できる仕組みが必要になる。本ADRではクラウド資源の作成や公開設定の変更は行わない。

- 登録地点と過去の記録は別の役割を持つ。設定変更を過去の記録へ反映する同期処理は設けない。
- 文書の構造が柔軟でも、アプリケーションで保存項目や値を検証する必要がある。
- 保存先の選定だけで、本人限定のアクセス制御が完了したとは扱わない。
- 読み書き・保存・通信などの利用に応じた費用を、作成前に確認する。無料枠は支出の強制上限として扱わない。
- 終了時は定期取得とアプリからのアクセスを止め、必要な記録を取り出した後に保存データを削除する方針とする。アクセスの遮断だけでは保存費用はなくならない。

### #55: PCから主観評価を入力し分析用データを出力する

- 主観評価の項目、尺度、各段階の基準。Gradient・Dramaticに対応する二項目と0〜4の尺度は提案段階であり、未確定。

両Issueで記録形式と権限の整合を確認する。#55 は #54 で定める記録形式を前提とし、保存済みの予報を変更せずに主観評価を追記する。
